把 Home Assistant 接进 AI 工作流：NAS 上重建、MCP 收窄权限，以及三个容易踩的坑

我想让自己的 AI 工作流（一套由几个常驻 agent 组成的流水线）能读家里智能设备的状态、开关几盏灯。先要有一个 Home Assistant（下面简称 HA）。我记得以前搭过一个 Docker 镜像，后来删了，所以第一步是找回来；找不到，才重建。

这篇记重建的过程，重点是三件事：新版 HA 里 MCP 集成改名了、小米集成有两个长得一样的入口、OAuth 登录回跳会跳到一个解析不了的域名。最后是怎么把 AI 能碰到的东西收窄到够用就好。

文中不出现令牌和账号；内网地址与真实环境一致。

一、TL;DR#

  • 旧的 HA 镜像没找到：ai-memory、Mac 上的 Podman 虚拟机、wenkangnas.local (192.168.1.4) 的 /volume1/docker、Gitea、GitHub、各台机器上的镜像列表都查过，唯一的线索是 Gitea 上一个 ha_xiaomi_home，它只是小米官方集成的原样副本，最后一次提交是 2025-04-28。真正值钱的是当时的配置目录，找不回来了。所以直接重建，配置目录放进会被快照的共享文件夹。
  • HA 跑在 NAS 的 Container Manager 里：官方镜像 + host 网络 + 8123，访问 http://192.168.1.4:8123。
  • AI 通过 HA 的 MCP 接口（/api/mcp）读写设备。我把它收窄成只剩 Assist 的设备控制（21 个工具），管理类工具全部去掉；只有 Claude 类 worker 配了这个 MCP，Codex、Grok、Kimi 都没有。
  • 三个坑：MCP 集成在 2026.11 里叫 “Model Context Protocol”；小米有两个入口，名字都带 “Xiaomi Home”；小米登录回跳到 homeassistant.local，Mac 解析不了。

二、重建：compose 文件#

NAS 上已有一个同样模式的服务（syno-sheet），我照它的目录结构放：

/volume1/docker/homeassistant/
├── docker-compose.yml
└── config/

compose 的要点只有三条：

  • 镜像用官方的 ghcr.io/home-assistant/home-assistant:stable。先从 NAS 上直连和走本机 3128 代理各测了一次 ghcr.io，直连就通，所以不需要镜像站。
  • network_mode: host。小米设备在局域网里的发现靠 mDNS/SSDP，桥接网络收不到。
  • 配置挂到 ./config，这个目录在 NAS 每天的快照范围里（后面验证过）。

启动那一步卡在 sudo：AI 用的账号在 NAS 上跑 docker 要 sudo 密码，AI 没有。我自己在终端里跑了：

ssh -t nas 'cd /volume1/docker/homeassistant && sudo docker compose pull && sudo docker compose up -d'

第一次拉镜像要一两个 GB。我让 AI 起了一个监控循环：每 10 秒 curl 一次 8123，同时看 config/ 里有没有文件、home-assistant.log 里有没有新的 ERROR。容器起来后 8123 返回了引导页（onboarding），日志里没有错误；管理员账号和家庭位置是我自己在页面里建的。

等它起来的这段时间，AI 顺手把小米官方集成（XiaoMi/ha_xiaomi_home，当时最新 v0.5.0）从 GitHub release 解压到了 config/custom_components/xiaomi_home/。自定义集成要重启 HA 才会加载。

三、三个坑#

3.1 坑一：找不到 “Model Context Protocol Server”#

AI 一开始让我在「设备与服务」里添加 Model Context Protocol Server。我搜不到。

AI 用浏览器自动化（我的 Chrome）打开 http://192.168.1.4:8123/config/integrations/dashboard 去看，发现在这个版本（2026.11）里它叫 “Model Context Protocol”，没有 “Server” 后缀；添加向导里也不再让你选 Assist。既然这本来就是我要做的第 3 步，它就在向导里直接点了提交。之后 MCP 接口就在：

http://192.168.1.4:8123/api/mcp

3.2 坑二：两个 “Xiaomi Home”#

搜 “xiaomi” 会出现两个看起来一样的入口：

入口实际是现象
内置的 xiaomi_miio老的核心集成要你填每台设备的 IP 和 32 位 token，一台一台加
带自定义集成图标的 “Xiaomi Home”我们装的 xiaomi_home第一屏是用户协议，然后选云服务区域，再跳到小米账号授权页

我第一次点进去的是前者，截图发给 AI，它一眼看出来是老集成，让我关掉。直接打开下面这个链接最稳，不用在搜索结果里挑：

http://192.168.1.4:8123/config/integrations/dashboard/add?domain=xiaomi_home

进对了以后有一个「网络检测地址」的输入框。留空会用内置默认值，默认值里可能有 8.8.8.8 这类国外地址，在国内 ping 不通时集成会以为断网。AI 先从 NAS 上测了小米账号、HTTP API、设备 spec API 和 MQTT 的 8883，都能通（约 0.2 秒返回 200），然后建议填 223.5.5.5,https://www.baidu.com，并勾上「检查网络依赖」。

3.3 坑三：登录成功了，但页面没跳转#

小米账号授权完，浏览器停在一个"成功"的页面，HA 这边没有任何反应。地址栏里是这样的：

http://homeassistant.local:8123/api/webhook/<一串数字>?code=<code>&state=<state>

回跳地址用的是 HA 自己认为的名字 homeassistant.local，而这个名字在我的 Mac 上解析不了，所以 HA 从头到尾没收到授权码。

办法是把同一个 URL 里的主机换成 NAS 的 IP，立刻用 curl 打一次（授权码很快就过期）：

curl -s --noproxy '*' 'http://192.168.1.4:8123/api/webhook/<一串数字>?code=<code>&state=<state>'

返回 “Authentication Successful”，回到 HA 页面它就自己进入了选择家庭、选择设备的那一步。

一劳永逸的改法：「设置 → 系统 → 网络 → Home Assistant URL」，把「本地网络」那一栏改成 http://192.168.1.4:8123。以后令牌过期重新授权，回跳就会走 IP 而不是 .local 名字。

四、接进 AI 工作流：权限收窄#

HA 的 MCP 接口用长期访问令牌（Long-Lived Access Token）认证。令牌我在 HA 的个人资料页里自己创建。AI 收到以后只做了这几件事：

  1. 存成本机一个权限 600 的文件（umask 077），不写进任何仓库。
  2. 通过 HA 的选项流把 MCP 收窄成只有 Assist API：读设备状态、开关灯和插座、调风扇、媒体、待办，一共 21 个工具。改配置、跑模板、读日志这类管理工具都不在里面。
  3. 在跑 worker 的那台机器（fleet-work）上写一个安装脚本，令牌通过 stdin 传入，只写进 ~/.claude.json 的 mcpServers.home。这样令牌既不出现在命令行参数里，也不进日志。脚本最后会真的调一次 tools/list 自证。
  4. 只给 Claude 类 worker 配。Codex、Grok、Kimi 都不加；中台总经理派活的规则也加了一条：涉及家里设备的任务，一律标成"只给 Claude"的数据级别。

验证用了一次真实的只读调用：让一个 Claude（Haiku，省额度）worker 调 GetLiveContext 读一次家里的状态，它读出台灯现在是关的。脚本自己输出 home MCP ok: 21 tools，看板的「组件」区也多了一个「智能家居」节点，健康检查用 HA 的 /api/。

4.1 公开给 AI 的设备：89 → 21#

HA 里每个实体可以单独决定要不要开放给 Assist（Expose）。第一次导入小米设备后，开放了 89 个，其中很多是插座的「保护」「指示灯」「童锁」「定时」这类设置开关，还有门铃的移动侦测、音箱静音。AI 通过 HA 的 WebSocket API 把它们列出来，批量取消，只留 21 个：灯、几个插座的总开关、落地扇、空气净化器、音箱，以及温湿度、PM2.5 这类只读传感器。

同时关掉了「新实体默认开放」（homeassistant/expose_new_entities/set）。以后加的设备，要我自己去勾，AI 才看得到。

4.2 备份#

上次丢就是因为没备份，这次补上：

  • HA 自带备份：每天 03:30 一次，保留 7 份，存在 config/backups/，也就是 NAS 的 /volume1/docker/homeassistant/config/backups/。通过 WebSocket 的 backup/config/update 配置，并手动做了第一份（约 2 MB）。
  • 这些备份没加密，里面有小米账号的登录令牌，所以只放在 NAS 上。
  • NAS 的快照每天 04:00，保留 14 天。AI 没有权限看 Snapshot Replication 的设置，我自己看了一眼，docker 共享文件夹显示「已计划」，所以配置和备份都在快照里。

**缺口要说清楚：**这两层都在同一台 NAS 上，NAS 的硬盘坏了会一起丢。真要防这个得再放一份到机器之外，我还没做。

五、几个顺带发现#

  • 温度读出来是 71.6、74.1：HA 初始设置时选了英制，其实是华氏度。改 unit_system 为 metric 只影响以后新建的实体，已有的温度传感器不会自动换算，AI 又一个一个把 8 个温度传感器的显示单位改成 °C。
  • 8 盏灯里 7 盏、52 个开关里 46 个显示「不可用」：日志里没有报错。我去米家 App 看了，确实是设备离线，不是集成的问题。
  • AI 在浏览器里点错过一次：它的几次按键在 Chrome 里打开了一个 “My Home Assistant” 页面，什么也没提交，随后关掉。这类浏览器自动化适合读页面、点明确的按钮，涉及账号登录的步骤我都留给自己做。

六、没验证的#

  • NAS 重启后的自启：我没有重启 NAS 验证 HA 容器能不能自己起来，compose 里的重启策略也没有单独读回去核对。
  • 微波炉那类插座：总开关留在了开放列表里。AI 提醒过：关的是插座电源，不会让微波炉启动；不想让 AI 碰就在 Expose 里取消。我暂时没动。
  • 异地备份：如上，没做。

七、小结#

  1. 找不回来的东西别再花时间找：把能想到的地方查一遍，确认镜像没了就直接按官方镜像重建，把配置放进快照范围，比继续翻历史省事。
  2. 新版本的名字会变：文档和 AI 的记忆都可能是上一个版本的叫法，找不到入口时让它打开页面去看，比反复搜索快。
  3. 长得一样的入口先看它要什么：要你填 IP 和 32 位 token 的，一定是老的那个。
  4. OAuth 回跳失败，先看地址栏里的主机名：授权码已经在 URL 里了，换成能解析的地址再打一次就行。
  5. 给 AI 的权限，默认关，按需开：89 → 21，再关掉「新实体默认开放」，是这次最值的两步。
