把 Steam Deck 改造成家里的 AI 算力节点：iSCSI 数据盘、llama.cpp，以及 SteamOS 的自动挂载

一台 Steam Deck（SteamOS 3.9.5，14 GB 内存，APU 共用显存）闲着。我想让它专职当家里的 AI 算力节点：删光游戏，数据放 wenkangnas.local (192.168.1.4) 上的 iSCSI 盘，跑一个小模型对局域网提供 OpenAI 兼容接口。

这篇按顺序记整个过程，重点是三个会让你白折腾的点：SteamOS 是只读根文件系统，装东西要放对地方；iSCSI 盘被系统自带的自动挂载抢了；下载模型时旁路网关的出站速度只有几 KB/s。

文中不出现任何账号和密码；内网地址与真实环境一致。Deck 的地址是 DHCP 分配的，会变。

一、TL;DR#

步骤做法
清游戏先 steam -shutdown 再删文件；SD 卡已用空间 214 G → 56 K
关 Steam 自启用户级 autostart 覆盖 Hidden=true + steamosctl set-default-login-mode desktop
数据盘NAS 上 1 TiB 的 iSCSI LUN，整盘 ext4，挂到 /srv/ai-data
open-iscsi用 pacman --root /opt/open-iscsi … 装到 /opt，SteamOS 升级不会冲掉
推理llama.cpp b12359 的 Vulkan 版 + Qwen3.5-4B（Q4_K_M，2.7 GB），监听 :8080
速度生成 16–19 tok/s，读 prompt 约 220 tok/s；iSCSI 读约 110 MB/s、写约 94 MB/s

还没做的：整机重启验证（Deck 桌面上开着终端，我没动）。所以"开机自动恢复"这一条，我只验证了分步骤的部分，没有一次完整的冷启动。

二、清游戏：先让 Steam 退出#

SD 卡里有 8 个游戏（其中两个没下载完，残留在 downloading/），加上 Proton 和 Steam Linux Runtime 共 2.1 G。

直接删文件会被 Steam 反写回去——它退出时会把游戏的安装记录（appmanifest）重新写一遍。所以顺序是：

  1. steam -shutdown，等它真正退出；
  2. 删 SD 卡上 steamapps/ 里的游戏、downloading/、运行组件；
  3. 按它原来的自启方式重新拉起（systemd 的 app-steam@autostart.service），看它重新扫描：库里没有任何应用，也没有自己重新下载什么。

保留的是 Steam 客户端本身，以及内置盘上 180 M 的 Steamworks Common Redistributables（删了它也会自己装回来）。

关掉 Steam 自启#

两步，缺一步重启后 Steam 还会起来：

# 1. 用户级覆盖：复制系统的 autostart 文件，在 [Desktop Entry] 下面加一行 Hidden=true
cp /etc/xdg/autostart/steam.desktop ~/.config/autostart/steam.desktop
#    （加入 Hidden=true）

# 2. 默认登录进桌面模式，而不是游戏模式（游戏模式本身就会拉起 Steam）
steamosctl set-default-login-mode desktop

要改回去：steamosctl set-default-login-mode game，再删掉 ~/.config/autostart/steam.desktop。

三、iSCSI 数据盘#

3.1 先想清楚装在哪#

SteamOS 的根文件系统是只读的 btrfs。/etc 通过 overlay 保留，/home、/opt、/srv、/var/lib/docker 是挂在 home 分区上的 bind mount，OS 升级后都还在。/var 是每个系统槽各一份，升级后可能被换掉。

所以 open-iscsi 不能直接 pacman -S（装到只读根里，升级就没了），而是装到 /opt：

pacman --root /opt/open-iscsi --dbpath … --gpgdir /etc/pacman.d/gnupg -dd --noscriptlet …

要注意两点：

  • 二进制要用 LD_LIBRARY_PATH=/opt/open-iscsi/usr/lib 才能找到库，所以 iscsiadm 我包了一层脚本。
  • pacman 在某个配置的仓库数据库缺失时会直接拒绝继续。这次 holo、core、extra 的库下载成功了，其余没成功，于是给它一份只列这三个仓库的临时配置文件，用完即删。

3.2 NAS 一侧#

NAS 上建了一个 1 TiB 的 LUN（精简配置），max_sessions=1、不开 CHAP（仅内网使用）。

iSCSI 一个关键参数：

node.session.timeo.replacement_timeout = -1

默认情况下 iSCSI 会话掉线一段时间后会向上层报 I/O 错误。设成 -1 是让 I/O 排队等待。这台 NAS 当时开着 DSM 的自动安装更新，更新会重启，我希望模型服务在 NAS 重启期间只是卡住、不是报错退出。

3.3 文件系统和挂载#

整块盘直接做 ext4，不分区。LUN 是精简配置，所以建文件系统时跳过 discard，并告诉 mke2fs 盘是预先清零的：

mkfs.ext4 -m 0 -E nodiscard,assume_storage_prezeroed=1 <device>

fstab 里的挂载选项我用了：discard、_netdev、nofail，以及 x-systemd.requires、x-systemd.device-timeout。意思是：网络起来之后才挂、挂不上不拖慢开机、盘的登录由 nas-iscsi.service（负责 iscsiadm 登录）先于挂载完成。

启动链是：

remote-fs.target → srv-ai\x2ddata.mount → nas-iscsi.service → iscsid.service

llama-server 单元用 WantedBy= 这个挂载点加 RequiresMountsFor，所以盘没挂上它就不启动，也不会反过来拖慢开机。

实测吞吐：读约 110 MB/s、写约 94 MB/s，基本跑满千兆网口。

四、坑：SteamOS 的自动挂载会再抢一次#

挂载做完，我发现 /srv/ai-data 上叠着两层。看 /proc/self/mountinfo 和 journal：

  • 内核识别出新的块设备以后，udev 会运行 SteamOS 的 block-device-event.sh；
  • 它把挂载交给 holo-automount.sh，通过 udisks 去挂；这套逻辑是给 SD 卡和 U 盘用的；
  • 结果是：对我这块 iSCSI 盘，它先跑了一遍 fsck -y，再在已经挂好的 /srv/ai-data 上重复挂了一层。

对一块要放模型的盘来说，自动对它跑 fsck -y 是我不想要的。修法是加一条 udev 规则，把这块 iSCSI 盘从 holo 的自动挂载里排除：

/etc/udev/rules.d/98-iscsi-no-holo-automount.rules

（规则本身是 AI 写的，我没有在文章里贴出它的内容，因为我只核对了效果，没有逐条核对匹配条件。）

修完以后我把 iSCSI 断开，再按开机流程重新登录挂载了一遍：现在只剩一层，模型服务在约 29 秒内恢复。

五、下载模型：为什么要绕开旁路网关#

5.1 现象#

下 llama.cpp 和模型很慢。AI 测了几组：

  • 经旁路网关 192.168.1.254（192.168.1.254）：5–20 KB/s，国内镜像也是这个速度。不是只有走代理的目标慢。
  • Deck 绕开它、直接走主路由 192.168.1.1（192.168.1.1）：约 21 MB/s。
  • 在路由器自己身上直接测，速度也一样慢；ping 出口正常（约 163 ms，不丢包）。所以慢的是走代理的流量，不是链路断了。

原因我没有查到：可能是出口那一头的服务器，也可能是到那个地址的流量被限速。这一条我没有修，只是标记给自己。更麻烦的是，旁路网关上的自动切换脚本只用很小的请求探活，检测不到这种"能通但极慢"的状态，当晚一次都没切；而且 AI 对比测了另一种协议的节点，同样慢，所以就算切过去也没用。

5.2 临时办法#

  • 给下载目标加几条 /32 主机路由，下一跳指到 192.168.1.1；下完就删（脚本里 trap 保证清理）。
  • ModelScope 的 CDN 限制单连接约 1–1.5 MB/s，所以用 8 路并行 range 下载，把一个 2.6 GB 的文件拼起来。

六、推理服务#

6.1 llama.cpp#

GitHub 上 ggml-org/llama.cpp 的 “latest” 发布这次是个坑：它的资产里只有一个 nightly-tag.txt，里面写的是构建号 b12359。所以要按这个 tag 去取具体的 release，下载 llama-b12359-bin-ubuntu-vulkan-x64.tar.gz，装到 /opt/llama.cpp/b12359，再用 current 软链指向当前版本，方便以后换。

跑在 Vulkan 后端上（RADV，统一内存）。模型全部放到 GPU 上算。

6.2 模型和默认参数#

  • Qwen3.5-4B，Q4_K_M，2614 MiB；
  • 上下文 32K；显存加 GTT 共占约 5 GB，机器还剩约 8.8 GB；
  • 默认关闭"思考"：服务端 --chat-template-kwargs '{"enable_thinking":false}'，短问题 1 秒内出答案。单次请求想思考，在 body 里加 "chat_template_kwargs": {"enable_thinking": true}；一道简单乘法在思考模式下大约要想 18 秒。

调用：

curl http://192.168.1.217:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.5-4b","messages":[{"role":"user","content":"你好"}]}'

浏览器打开 http://192.168.1.217:8080 有 llama-server 自带的聊天页。

6.3 注意事项#

  • 接口没设 API key，CORS 也是全开。firewalld 的 public 区本来就放行 1024–65535，所以局域网里直接能访问。只适合内网用，要让别处能访问，先加 --api-key。
  • 不给 system prompt 问它是谁，它会说自己是 Google 训练的。这是模型本身的毛病，加个 system prompt 就行。
  • Steam 关了自启，就不再常驻占用约 1.7 GB 内存（总共只有 14 GB，GPU 还共用它）。内置盘 /home 只剩 42 GB，所以模型和数据都放 iSCSI 盘。

七、顺带：Deck 的 IP 为什么有三个#

另一天我顺路扫了 192.168.1.0/24 的 22 端口找这台 Deck，发现同一台机器有线网卡同时有两个地址（.152 和 .217），Wi‑Fi 还有一个 .218。

  • NetworkManager 的日志显示它重启后重新拿了 DHCP：有线 .217、Wi‑Fi .218；
  • .152 是有线网卡上没释放的旧地址，连接配置是自动获取，不是我手动设的；
  • 我让它把 .152 去掉了：先从 .217 登录确认可用，再 ip -4 address delete 192.168.1.152/24 dev <有线网卡>。核对后路由里的旧 .152 条目也一并消失。

如果希望 SSH 地址长期稳定，要在 DHCP 服务器（也就是 NAS）上给 Deck 的有线网卡做地址保留。我还没做。另外那天顺手把 sshd 设成了开机启用（之前是运行中但没 enable）。

八、没验证的#

  1. 整机冷启动：只验证了 “断开 iSCSI → 按开机流程重新登录挂载 → 服务 29 秒恢复”，没有真的重启 Deck。
  2. udev 规则在 SteamOS 大版本升级后是否还在：/etc 是 overlay，理论上保留，没有验证。
  3. 旁路网关限速的根因：没查。

九、可复用的清单#

  1. SteamOS 上装东西，先问"升级后还在吗"：放 /opt、/home、/srv，别放 /usr、/var。
  2. iSCSI 给长时间运行的服务用，把 replacement_timeout 设成 -1，宁可卡住也别让上层看到 I/O 错误。
  3. SteamOS 的自动挂载逻辑对任何新出现的块设备都生效，包括 iSCSI。看到挂载点上叠了两层，先看 udev 规则。
  4. 下载慢先区分"链路慢"还是"代理慢"：同一台机器绕过代理再测一次，差十倍就是代理那一侧的问题。
  5. 探活脚本只测"能不能连"，测不出"极慢"。真要做自动切换，得把一个小下载的速度也算进去。
