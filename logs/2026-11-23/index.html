这两周的底色是把家里的机器和 AI 工作流（agent-fleet）互相接起来、再把风险一件件摸清：新装了 Home Assistant 和一台 Steam Deck 算力节点，扩容了一台小主机，给 NAS 的系统升级做了一套带窗口限制的流程；中间被一个 macOS 的老开关又坑了一次。

Home Assistant 在 NAS 上重建，并以最小权限接进 AI 工作流#

以前搭的 HA 镜像怎么也找不到，直接用官方镜像在 wenkangnas.local (192.168.1.4) 的 Container Manager 里重建，配置目录放进每天快照的共享文件夹。AI 通过 HA 的 MCP 接口控制设备，我把它收窄到只剩 Assist 的 21 个工具，开放给它的实体从 89 个减到 21 个，并关掉了「新实体默认开放」；只有 Claude 类 worker 配了这个 MCP。踩的坑有三个：新版里 MCP 集成改名了、小米有两个都叫 “Xiaomi Home” 的入口、OAuth 登录回跳到解析不了的 homeassistant.local。完整过程见《把 Home Assistant 接进 AI 工作流》。

Steam Deck 改成 AI 算力节点：iSCSI 数据盘 + llama.cpp#

删光游戏、关掉 Steam 自启，把 NAS 上一个 1 TiB 的 iSCSI LUN 挂到 /srv/ai-data，用 llama.cpp 的 Vulkan 版跑 Qwen3.5-4B，对局域网提供 OpenAI 兼容接口（生成 16–19 tok/s）。两个有意思的点：SteamOS 自带的自动挂载会在我已经挂好的 iSCSI 盘上再叠一层并跑 fsck -y，要用 udev 规则排除；下载模型时发现经旁路网关 192.168.1.254 只有几 KB/s，绕过它走主路由有约 21 MB/s，根因我没查。写成了一篇：《把 Steam Deck 改造成家里的 AI 算力节点》。整机冷启动我没验证。

NAS 系统升级：DSM 加进上游巡检，升级走带时间窗的流程#

DSM 7.4.1-90080 Update 2 是 11-20 发的纯安全补丁（Synology-SA-26:20，nginx 处理 HTTP/2 的问题，群晖标 Critical；SA-26:21 在评估时已经公开，会话里写的是 OAuth API 的免登录漏洞、CVSS 9.8，这两条的细节我没独立核实）。中文版发布说明比英文版早几天列出新版本，所以巡检要查中文源。我做了几件事：

  • 把 DSM 加进 agent-fleet 的上游巡检，在用版本改成 SSH 读 NAS 的真实版本，用一把锁死的只读密钥：不管客户端让它跑什么，NAS 只执行一个固定的查版本脚本，只接受来自 fleet-work 的登录，不给终端、不给端口转发。我从 fleet-work 上用 id、建文件、端口转发都试过，都被挡住。
  • 把 DSM 的自动更新从"每周日 02:25 自动装安全更新"改成只通知。
  • 再配了一把升级专用密钥，只能做检查、下载、安装；NAS 自己也拒绝在工作日 08:30–18:00 安装。写了「NAS 升级」规则：评估 → 发卡片 → 我批准 → 到窗口前再检查一遍（有 agent 在跑活就顺延，最多等 2 小时）→ 安装 → 验证。独立评审找出 11 个问题，修完后 47 个测试通过。
  • 一个我自己说错的地方：重启期间旁路网关是 NAS 上的虚拟机，它一停，连 fleet-work 也没有网关，agent 既不能调模型接口也发不出通知。所以流程里写了"约定时间过了半小时还没收到’好了’就是出事了"。

到会话结束时 Update 2 的安装包下好了，卡片在等我批准，还没有真的装。

中台加了「流水」：点中台节点就能回溯发生过什么#

AI 工作流的中台（agent-autoloop）原本设计成所有入口都从它过，可在看板上点它什么也看不到。查下来它是事件溯源的：所有改变状态的输入都往 SQLite 的 facts 表追加一条，从不压缩。我让 AI 在看板里加了一个把这些记录逐条翻译成人话的模块，线上 9600 多条历史记录只读、内容打码跑了一遍，0.7 秒翻完，没有读不懂的；点中台节点出「流水」栏，带筛选、搜索和"来龙去脉"的溯源，原始记录要登录才能看。后端和界面的测试（137 个）都过了，本机用假数据在浏览器里点过一遍。我读到的素材停在提交 PR 之前，上线和合并的结果我没看到。

多开 sub-agent 能不能提速：取决于卡在哪一段#

我让 AI 审计一遍看板。它起了几路审查，我问"多 fork 几个是不是更快"。答案是分段看：按时钟走的健康采样（40 分钟）加人没用，逐条核验这种能拆开的才有用。于是把核验按面拆成 12 个并行，再补 4 个，一共 16 个，预估从 30–60 分钟降到 10–15 分钟（这是估计）。审计结论里印象最深的一条是：点击确认、状态灯和回话三样都不可信——离线演练里，过期的「同意」按钮点了照样会约 20 分钟后装 DSM 并重启；在「别的想法」里打字"今晚再升"会被当成"这版不升"。这几条我还没修，修之前就按它写的用法点。

小主机 192.168.1.5：内存加到 48 GB，第二块 SSD 挂成 /home#

给这台 EliteDesk 800 G6 Mini 加了内存和一块 256 GB 的 NVMe。内存 48 GB 全认到了（跑 2667 MT/s，应该是 CPU 限制；一条 16 GB 加一条 32 GB，多出来的部分是单通道）。SSD 第一次开机没认到，查到这台有两个 M.2 存储槽加一个 WLAN 槽，第二个存储槽据说在 2.5" 托架下面；我重新装了以后它出现了（盘是旧的，带 Windows 分区），格式化成 ext4 挂到 /home，fstab 里加了 nofail。迁数据时有个坑：有进程还在往旧 /home 里写（一个 rootless podman 容器），所以要先停服务、再做最后一次 rsync、再启动，并用 mount --bind / 看旧根上的 /home 才能清干净。顺带插了一个 HDMI 欺骗器，让没接显示器的机器也能经 AMT 远程看到画面；分辨率通过内核参数 video=HDMI-A-1:640x480@60 压到最低。重启验证通过：/home 自动挂上、两台虚拟机自启。一个无关的 dnscrypt-proxy-resolvconf 一直启动失败，我直接 mask 了，DNS 本身没受影响。

一个自用的下载代理容器，从 Mac 搬到小主机#

Mac 上用 Apple container 跑的这个容器突然起不来，自启脚本每分钟重试，两天近千次失败，日志里只写了 FAILED 没写原因。根因是容器根文件系统坏了（EXT4-fs error … doubly allocated），表面报错却是 configureDns。数据卷里没有要保留的东西，我删了重建，然后决定搬到常开的 192.168.1.5：rootless podman + quadlet，数据卷整个拷过去，下载目录走 NFS 写到 NAS 上。NFS 有个坑：downloads 共享的根目录用的是群晖 ACL，NFS 上显示成 d---------，要挂子目录。搬完后一度出现页面黑屏，和迁移无关，是对方的前端更新后旧版的 JS 改写规则对不上，合并上游最新版后恢复。教训：自启脚本的失败日志要写原因。

摸清三台机器的依赖，顺手把 DHCP 租期从 100 分钟改成 1 天#

让 AI 看 wenkangnas.local (192.168.1.4)、它里面的 Virtual DSM（192.168.1.44）和 192.168.1.5 之间哪些能迁走来降低互相依赖。几个结论：1.44 不是独立机器，是 NAS 里的 VMM 虚拟机，NAS 宕机它也挂，而且这个免费的 Virtual DSM 许可只能跑在 NAS 里，迁不走；DHCP 是 NAS 在发，租期只有 6000 秒，NAS 宕机一两小时后家里设备会陆续掉线。我选择只改租期。改的时候踩了 DSM 接口的坑：读出来的租期单位是分钟，写进去却按秒算，写 1440 变成了 24 分钟；而且这个接口会把同一个值覆盖到所有网段，把另外两段原本永久的租约也改成了短租期。AI 随后发现并修了：主网段改成 86400 秒、手工把两个静态网段改回永久、重启服务；改之前备份了 /etc/dhcpd。以后在 DSM 界面里保存任何 DHCP 设置，这两段很可能又被覆盖，要再检查。另外，过程中明文密码出现在聊天里，已经提醒要换。

Windows 虚拟机迁到 libvirt 之后：qemu-ga 每 5 分钟崩一次#

finash-vm.local (192.168.1.139) 迁到 192.168.1.5 的 libvirt 以后体检，系统日志里群晖 Guest Tool 的 qemu-ga 从迁移那天起每 5 分钟启动、退出一次，7 天累计崩了 1970 次（我的推测是它在等群晖 VMM 的心跳，换了虚拟化平台就等不到，没有直接证据）。要卸，但不能走「程序和功能」里的标准卸载：它会顺带运行驱动卸载脚本，把启动盘的 VirtIO SCSI 驱动一起删掉，机器就起不来。AI 按它自带的 windows-agent-uninstaller.bat 的步骤只删了 qemu-ga 和 VSS 服务，并给那个卸载入口加了 NoRemove。没有 agent 以后宿主机只能靠 ACPI 电源键关机，而 Windows Server 默认不响应，所以设 ShutdownWithoutLogon=1、把电源键动作改成关机。实测从宿主机发 ACPI 关机，15 秒干净关掉。驱动没换，原因是现在的驱动不旧、运行稳定，换启动盘驱动的风险大于收益。

克隆一台 OpenWrt 当流量测试机，顺带改了 DHCP 的网关#

要一台和 192.168.1.254 一样、但配置很低的测试机。做法：在 NAS 上对旁路网关的系统盘用 cp --reflink=always 做瞬时拷贝，压缩后经 SSH 流到 192.168.1.5，开机之前在镜像里离线改好 IP（改成 .253）、主机名和 IPv6 ULA 前缀，所以网上从来没有出现过两个 .254；在 libvirt 里用 1 核 512 MB 起来（开机后内存还剩约 240 MB）。分流配置里凡是会和原机互相踢的共享凭据都改成走默认出口。接着发现 .253 早就被另一个网关容器占着，于是把那个容器改到了 .252；这一步没有被要求但必须做：NAS 的 DHCP 给其中一段地址（里面有我的手机）下发的网关写的是 .253，不改的话手机会把测试机当网关，我把它改成 .252 并确认服务重启后配置还在。手机要重新续租或重连 Wi-Fi 才会拿到新网关，这条我没有逐台验证。

ESP32-P4 小屏：延迟拆开测、硬件旋转、跟着 Mac 亮灭屏#

三件事。延迟：用 2K 摄像头拍屏、同时从 NAS 拉同一路流，对比画面里时钟的跳变，总延迟约 1.9 秒，其中摄像头到 NAS 转码这段约 1.15 秒、NAS 到板子上屏约 0.8 秒；把 LVGL 的整屏软件旋转（每帧约 110 ms）换成 ESP32-P4 的 PPA 硬件旋转后，帧率 8 → 10 fps，总延迟降到约 1.75 秒，板子这段约 0.6 秒，再往下抠收益很小。Mac 关机后屏幕闪烁：判断是供电问题（板子靠扩展坞的 USB 口，Mac 一关机就反复掉电重启，电池一直插着电却只有 26%），没有验证，因为我没有条件换独立充电头来测。省电：Mac 连不上超过 60 秒就黑屏，重新连上约 1 秒亮屏，熄屏时再把 Wi-Fi 省电打开、停掉动画刷新。顺手追了一条无关的 esp_cache_msync 报错，根因是固件把低功耗 SRAM 也当普通内存分配，LVGL 的一块绘图缓冲正好分到那里，关掉 CONFIG_ESP_SYSTEM_ALLOW_RTC_FAST_MEM_AS_HEAP 后报错没了。降 CPU 频率做不了，因为屏幕驱动一直把它锁在最高频。

macOS 的"允许在后台"又关了一次：这次连带 OpenVPN Connect#

NetBird 的老问题复发了：netbird up 报找不到 /var/run/netbird.sock。这次查明开关是 11-03 11:48:50 被关的，查不到是谁关的。过程中发现一个坑：照着报错提示不带 sudo 跑 netbird service start，会把 daemon 的 plist 错载进用户域，一直以退出码 78 失败重试，我把它卸掉了；别照那条提示跑。三天后（11-21）我又发现 Mac 上 OpenVPN Connect 在外面拨不回来，日志里 407 次连接全是 socket_protect error——不是网络，是它依赖的 ovpnagent 后台程序没跑，原因同样是系统设置里对应开关被关（sfltool dumpbtm 里状态是 disallowed）。临时用 sudo launchctl bootstrap system …plist 拉起，永久修好只能我自己在「登录项与扩展」里打开开关。验证开关生效看 dumpbtm：ovpnagent 和 ovpnhelper 从 0x9 变成 0xb。重启后能否自启，两次我都没实测。

2K 摄像头偏肉色：自动白平衡被关了#

画面发黄。用 libusb 写了个读写 UVC 参数的小工具，读出摄像头的自动白平衡是关的，固定在一个手动值上。同一块白色纸巾，修复前 R/G 0.93、B/G 0.64，打开自动白平衡后 1.05、0.95（1.00 为纯白）。重新开流、USB 软重置、拔掉重插后设置都还在，因为参数存在摄像头里。谁关的没查到；再偏色时重新执行一次开关命令就行。

Codex 的 computer-use 显示 failed (0 tools)#

~/.codex/config.toml 里这个 MCP 的启动命令用了相对路径 ./Codex Computer Use.app/...，而程序装在 ~/.codex/computer-use/，从别的目录启动就找不到。改成绝对路径、备份原配置后，MCP 连接返回 10 个工具；当前会话要重新加载 MCP 或重启 Codex 才能更新状态。顺带试了让 Codex 代为按键，它被 computer-use 的安全策略拦在 iTerm2 外面，这一条符合预期，我也没有去绕。

ai-memory 索引整理#

给自己写了一份"英语交流"偏好，写进 ~/.claude/CLAUDE.md 和 ai-memory；然后把 memory-index 补登了 41 条没在索引里的条目，把 7 个看不出内容的自动生成 id 改成可读名（旧条目标成 superseded 并留跳转）。看板上的 /book 是按这份索引现生成的，一分钟内会同步。两个小坑：看板把双方括号当成链接语法吃掉了，序里的那句话要改成文字；与另一个 agent 同时想改索引时，写入带上 expected_rev，后写的会被拒绝而不是悄悄覆盖。
